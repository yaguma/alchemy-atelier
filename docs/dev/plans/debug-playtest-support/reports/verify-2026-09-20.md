## Confidence Summary

### 🟡 要確認（Medium Confidence）
- task 002: DebugPanelの半透明黒背景パネル（`debug_panel.tscn`、左上固定・`offset_right=160, offset_bottom=132`）が他画面のHUD要素（RankHud等）と実機で重ならないかは未確認。GdUnit4テストでは`visible`と描画順（子ノードindex）のみ検証しており、実際のピクセル位置の重なりまでは検証していない。`docs/dev/plans/debug-playtest-support/playtest-checklist.md`の手順で人間による目視確認が必要。

### 🔴 要判断（Low Confidence）
- task 001: `debug_jump_to_next_rank()`が末尾ランク（`is_true_final_rank()`がtrue）または次ランクのRankMaster未登録時に、何もしない（早期return）だけで成否を呼び出し元に伝えない設計になっている。Plan上は「本タスクのスコープ外」と判断済みとのことだが、QA担当がボタンを押しても無反応であることの意図が伝わりにくい可能性がある。UXとして許容するかは人間の判断に委ねる。
- task 003: `debug_jump_to_next_rank()`がシグナルを発行しない設計のため、`main.gd`で`DebugPanel.get_jump_rank_button().pressed`を`RankHud.refresh`に直接接続するという対応が追加されている（`debug_panel.gd`にも`get_jump_rank_button()`アクセサが追記されており、タスク003が当初宣言していたFiles一覧（`main.tscn`変更のみ）を超える変更である）。この設計判断（新規シグナルを追加せず既存Buttonの`pressed`シグナルを流用する方式）について:
  - `state-management.md`「UIコンポーネント間通信は直接の親子関係ならsignalを子が発行し親が`connect()`」という原則には形式的に沿っている（`DebugPanel`は`MainScene`の子であり、`Button.pressed`という既存の子シグナルを親が購読している）。
  - 一方で、意味的には「ランクが変わった」という`GameState`側のドメインイベントではなく「ボタンが押された」というUI入力イベントを`RankHud`更新のトリガーに使っている点は、`architecture.md`の「UIコンポーネント間通信は`GameState`のsignal経由」という基本方針（他の`phase_changed`等の設計）とはやや異なる。`debug_jump_to_next_rank()`自体に`rank_changed`相当のシグナルを追加発行させる設計の方が既存パターンと一貫するが、本Planでは意図的に「新規シグナルを増やさない」判断がされている。QA専用の限定的な配線であり実害は小さいが、将来同種のデバッグAPIを追加する際にこのパターンが踏襲されるかどうかはレビューで方針を確認しておくのが望ましい。
