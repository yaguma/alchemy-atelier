## ペルソナ

### ペルソナ1: 錬金術師見習い（プレイヤー）

- **役割**: ギルドランク制デッキ構築RPG「Atelier」のプレイヤー。庭で仕込んだ素材を調合し、完成した調合物をギルドへ納品してランクのノルマをこなす
- **目的**: 「今日の指定に合わせて作るか、自分の得意な組み合わせで作るか」を毎ターン判断し、貢献度（ノルマ削り）とゴールドの両方を伸ばしたい
- **技術レベル**: ゲームプレイヤーとしては初級〜中級。ギルド納品はプレイヤー操作なしの自動決算のため、本ペルソナの体験は「調合の結果として何が返ってくるか」に集約される（UI実装は別plan）

### ペルソナ2: 実装者（後続RankSystem・UI開発者）

- **役割**: 本plan完了後に`RankSystem`（rank plan）・日替わり指定の再抽選ロジック（別plan）・納品結果UI（別plan）を実装するエンジニア
- **目的**: `DeliveryResolver`の入出力契約（`null`許容・ボーナス適用の一元化）と`GameState`の納品API（消費するキュー・加算先・シグナル）が明確で、安心して差し替え・拡張できる状態にしたい
- **技術レベル**: 上級（本プロジェクトのアーキテクチャ規約を理解している）

## エピック1: 日替わり指定への合致判定

### US-001: 今日の指定品目に合わせて作りボーナスを得たい 🔵

**私は** 錬金術師見習い **として**
**ギルドが今日指定した品目（レシピ）と同じ調合物を納品したとき、貢献度と報酬の両方にボーナスが乗ってほしい**
**そうすることで** 「指定に合わせて作るか、手持ち素材で得意な物を作るか」というターンごとの判断に意味が生まれる

- **関連要件**: FR-003, FR-004, FR-101, FR-103
- **優先度**: Must Have
- **受入基準**: AC-001, AC-004, AC-007

### US-002: 今日の指定特性を宿してボーナスを得たい 🔵

**私は** 錬金術師見習い **として**
**ギルドが今日指定した特性（例: 聖）が発現している調合物を納品したとき、品目が何であってもボーナスが乗ってほしい**
**そうすることで** 庭での仕込み段階から「今日の指定特性を狙って素材を揃える」という先行投資の判断ができる

- **関連要件**: FR-003, FR-004, FR-102, FR-103
- **優先度**: Must Have
- **受入基準**: AC-002, AC-004, AC-007

### US-003: 指定に合わなくても本来の価値はそのまま納品されてほしい 🔵

**私は** 錬金術師見習い **として**
**今日の指定に合致しない調合物を納品しても、ボーナスが乗らないだけで貢献度・報酬がそのまま得られてほしい**
**そうすることで** 「指定を外したターンは丸損」にならず、素材の巡り合わせが悪い日でも前に進める

- **関連要件**: FR-104
- **優先度**: Must Have
- **受入基準**: AC-005

## エピック2: 納品の自動決算

### US-004: 調合した物が自動で納品されゴールドが増えてほしい 🔴

**私は** 錬金術師見習い **として**
**調合して納品待ちになっている調合物が、追加の操作なしにまとめてギルドへ納品され、報酬がゴールドに反映されてほしい**
**そうすることで** 「納品ボタンを押す」だけの作業に手間を取られず、庭と調合の判断に集中できる

- **関連要件**: FR-005, FR-105, FR-106, FR-301
- **優先度**: Must Have
- **受入基準**: AC-008, AC-009

### US-005: 貢献度が積み上がりランク進行の土台になってほしい 🔴

**私は** 錬金術師見習い **として**
**納品した調合物の貢献度が失われずに蓄積され、（後続のrank plan実装後に）ランクのノルマ削りへ反映されてほしい**
**そうすることで** 「貢献度寄りに作る」という選択が確かに前進につながっていると実感できる

- **関連要件**: FR-006, FR-107
- **優先度**: Must Have
- **受入基準**: AC-010

### US-006: 納品結果を件別に受け取って将来のUI表示に使いたい 🔴

**私は** 実装者 **として**
**納品完了時に、1件ごとの最終貢献度・最終報酬・指定合致有無を含む結果の配列をシグナルで受け取りたい**
**そうすることで** 納品結果画面で「指定合致！ +30%」のような件別のフィードバックを後から実装できる

- **関連要件**: FR-002, FR-108
- **優先度**: Should Have
- **受入基準**: AC-006, AC-011

## エピック3: 契約の堅牢性（後続plan・他Featureへの橋渡し）

### US-007: 昇格試験からnull指定で呼んでも安全に動いてほしい 🔵

**私は** 実装者 **として**
**昇格試験（rank plan）のように「本日の指定調合物が存在しない」局面で`daily_order`に`null`を渡しても、判定が必ず非合致となりクラッシュしないでほしい**
**そうすることで** RankSystem側は特別な分岐を書かずに同じ`DeliveryResolver`を再利用できる

- **関連要件**: FR-101, FR-201, FR-301, FR-407
- **優先度**: Must Have
- **受入基準**: AC-003

### US-008: 指定合致ボーナスが二重に掛からない保証がほしい 🔵

**私は** 実装者 **として**
**指定合致ボーナスの適用箇所が`DeliveryResolver.resolve`の一箇所だけに限定されていてほしい**
**そうすることで** 調合側（`ProductValueCalculator`）と納品側の両方で倍率が掛かる二重乗算バグを構造的に防げる

- **関連要件**: FR-001, FR-103, FR-403
- **優先度**: Must Have
- **受入基準**: AC-013, AC-014

### US-009: 未納品キューが空でも安全に呼べてほしい 🟡

**私は** 実装者 **として**
**納品対象が1件もない状態で納品処理を呼び出しても、失敗ではなく「納品0件の成功」として扱われてほしい**
**そうすることで** ターン終了処理から無条件に納品処理を呼ぶ実装にでき、呼び出し側で件数チェックを重複させずに済む

- **関連要件**: FR-109
- **優先度**: Should Have
- **受入基準**: AC-012

### US-010: get_state()の戻り値を書き換えても内部状態が壊れないようにしたい 🔵

**私は** 実装者 **として**
**納品処理の追加後も`GameState.get_state()`が返す`pending_products`を呼び出し元が変更したときに、`GameState`内部の正本データが汚染されないでほしい**
**そうすることで** UI側の実装ミスがゲーム状態の整合性を壊すリスクを構造的に排除できる

- **関連要件**: FR-408
- **優先度**: Should Have
- **受入基準**: AC-015

### US-011: RankSystem実装時に貢献度の蓄積先を差し替えられる形にしてほしい 🔵

**私は** 実装者 **として**
**貢献度の蓄積が`GameState`内の分かりやすい単一の暫定フィールドに集約され、本planではランクノルマの減算・降格判定・昇格試験を一切実装しないでほしい**
**そうすることで** rank plan側は当該フィールドを正式なノルマ管理へ置き換える作業だけに集中できる

- **関連要件**: FR-006, FR-404, FR-405, FR-406
- **優先度**: Should Have
- **受入基準**: AC-010, AC-016
