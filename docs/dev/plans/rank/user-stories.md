## ペルソナ

### ペルソナ1: 錬金術師見習い（プレイヤー）

- **役割**: ギルドランク制デッキ構築RPG「Atelier」のプレイヤー。庭で仕込んだ素材を調合し、完成した調合物をギルドへ納品してランクのノルマをこなす
- **目的**: 「制限ターン内にノルマを削り切れるか」という中期的な目標に向けて毎ターンの調合を組み立て、昇格試験への挑戦権を勝ち取りたい。失敗しても再挑戦できるが、無限には許されない緊張感の中で判断したい
- **技術レベル**: ゲームプレイヤーとしては初級〜中級。本planの範囲はUI未実装のため、本ペルソナの体験は「納品の結果としてノルマがどう減り、制限ターンで何が確定するか」という内部挙動に集約される

### ペルソナ2: 実装者（後続promotion-exam・ターンサイクル・UI開発者）

- **役割**: 本plan完了後に`PromotionExamResolver`（promotion-exam plan）・ターン進行の配線（ターンサイクル plan）・ランク進行UI（別plan）を実装するエンジニア
- **目的**: `RankQuotaResolver`/`TurnLimitResolver`の入出力契約と`GameState`のランクAPI（ノルマ消費・結果評価・降格確定・ゲームオーバー判定）が明確で、安心して後続の配線・拡張ができる状態にしたい
- **技術レベル**: 上級（本プロジェクトのアーキテクチャ規約を理解している）

## エピック1: ランクノルマの消費と進捗

### US-001: 現在ランクの審査基準がデータとして定義されていてほしい 🔵

**私は** 錬金術師見習い **として**
**「Gランクはノルマ100・制限15ターン・特性は封印」のようにランクごとの審査基準が明確に定義されていてほしい**
**そうすることで** 今のランクで何をどれだけ達成すべきかという目標が定まり、ターンごとの調合方針を立てられる

- **関連要件**: FR-004
- **優先度**: Must Have
- **受入基準**: AC-007

### US-002: 納品した貢献度の分だけノルマが確実に減ってほしい 🔵

**私は** 錬金術師見習い **として**
**ギルドへ納品した調合物の貢献度の分だけランクノルマ残量が減り、ノルマを超えて納品しても0で止まってほしい**
**そうすることで** 「貢献度寄りに作る」という選択が確かに前進につながっていると実感でき、超過分の扱いに不安を持たずに大きな納品を狙える

- **関連要件**: FR-101, FR-102, FR-108
- **優先度**: Must Have
- **受入基準**: AC-001, AC-002, AC-005, AC-009

### US-010: 貢献度の行き先が暫定フィールドから正式なノルマ管理に切り替わってほしい 🔵

**私は** 実装者 **として**
**guild planが暫定的に置いた累積貢献度フィールドが完全に撤去され、貢献度の唯一の行き先が現在ランクのノルマ残量になっていてほしい**
**そうすることで** 「貢献度がどこに積まれているか」の情報源が二重化せず、後続のUI・セーブ実装が参照先を迷わずに済む

- **関連要件**: FR-108, FR-408
- **優先度**: Must Have
- **受入基準**: AC-009

## エピック2: 制限ターンでの結果確定

### US-003: 現ランクでの経過ターンがゲーム全体のターン数と独立していてほしい 🔵

**私は** 実装者 **として**
**現ランクでの経過ターン（`elapsed_turn`）が、ゲーム全体で単調増加するターン数（`_current_turn`）とは別のカウンタとして管理されていてほしい**
**そうすることで** 降格して同一ランクに再挑戦したときに制限ターンを正しく数え直せる

- **関連要件**: FR-005
- **優先度**: Must Have
- **受入基準**: AC-008

### US-004: ノルマを早く削り切っても残りターンを自由に使わせてほしい 🔵

**私は** 錬金術師見習い **として**
**制限ターンより先にノルマを0にできたとき、即座に昇格試験へ飛ばされるのではなく残りターンを通常プレイに使わせてほしい**
**そうすることで** 素材の作り置き・ゴールド稼ぎといった「試験に向けた準備期間」として早期クリアの成果を活かせる

- **関連要件**: FR-003, FR-104, FR-105, FR-106, FR-411
- **優先度**: Must Have
- **受入基準**: AC-003, AC-004, AC-006

### US-005: 制限ターンでノルマが残っていたら同じランクに再挑戦させてほしい 🔵

**私は** 錬金術師見習い **として**
**制限ターン到達時にノルマが残っていた場合、ランク文字は下げずに同一ランクへノルマ・経過ターンをリセットして再挑戦させてほしい（庭・在庫・ゴールド・恒久投資は引き継ぎたい）**
**そうすることで** 失敗しても積み上げた資産は失わず、次の挑戦で挽回できる手応えが残る

- **関連要件**: FR-003, FR-103, FR-107, FR-110
- **優先度**: Must Have
- **受入基準**: AC-004, AC-006, AC-008, AC-011

### US-006: 再挑戦の回数に上限があり明確な詰みが存在してほしい 🔵

**私は** 錬金術師見習い **として**
**同一ランクでの再挑戦回数が規定回数に達したらゲームオーバーになってほしい**
**そうすることで** 「無限にやり直せるから何をしてもいい」ではなく、1ターン1ターンの判断に緊張感が生まれる

- **関連要件**: FR-007, FR-110, FR-111, FR-113, FR-202
- **優先度**: Must Have
- **受入基準**: AC-011

## エピック3: ランク由来の解禁と状態の権威

### US-007: 特性が使えるかどうかを現在ランクが決めてほしい 🔵

**私は** 錬金術師見習い **として**
**「特性が解禁されているか」がGランクでは封印・上位ランクでは解禁というように現在ランクによって決まってほしい**
**そうすることで** 「ランクを上げると新しい遊び方が開く」という進行の手応えが、調合の挙動そのものに現れる

- **関連要件**: FR-004, FR-114, FR-201
- **優先度**: Must Have
- **受入基準**: AC-007, AC-014

### US-009: ランク状態の変更経路が`GameState`に一本化されていてほしい 🔵

**私は** 実装者 **として**
**現在ランク・ノルマ残量・降格回数を変更できる経路が`GameState`のメソッドだけに限定され、`get_state()`の戻り値を書き換えても内部状態が壊れないでほしい**
**そうすることで** UI側の実装ミスがゲーム状態の整合性を壊すリスクを構造的に排除できる

- **関連要件**: FR-006, FR-109, FR-410
- **優先度**: Must Have
- **受入基準**: AC-010, AC-016

## エピック4: 後続planへの橋渡し

### US-008: ランク判定ロジックが副作用なしで単体テストできてほしい 🔵

**そうすることで** ランクバランスの調整時に、ゲームを起動せず数値の組み合わせだけで挙動を検証できる

- **関連要件**: FR-001, FR-002, FR-401, FR-402
- **優先度**: Must Have
- **受入基準**: AC-013

**そうすることで** 昇格試験画面への遷移やゲームオーバー画面の表示を、`GameState`をポーリングせずイベント駆動で後から実装できる

- **関連要件**: FR-112, FR-113
- **優先度**: Should Have

**そうすることで** コンテンツ作成planの完了を待たずにランク進行のロジックを検証でき、後続planも同じ手段でテストを組める

- **関連要件**: FR-301, FR-302
- **優先度**: Should Have
- **受入基準**: AC-015, AC-016

### US-013: 本planがスコープ外機能に手を出さないでほしい 🔵

**私は** 実装者 **として**
**昇格試験本体・ランク遷移・実データ作成・ターン進行の配線・UIが本planでは一切実装されず、後続planの担当範囲として空けられていてほしい**
**そうすることで** 各planの責務が重複せず、後続plan側は既存実装との衝突を気にせず着手できる
