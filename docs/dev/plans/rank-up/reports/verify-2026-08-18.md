## Issues Found

### Issue-1（🔴 要判断）: `_start_exam()`のnullガードが`commit_rank_outcome()`経由では到達不能

**該当箇所**: `atelier/autoload/game_state.gd` L484-495（`_start_exam()`）、L426-439（`evaluate_rank_outcome()`）、L452-470（`commit_rank_outcome()`）

`_start_exam()`はNFR-101対応として以下の二重ガードを持つ。

```gdscript
func _start_exam() -> void:
    var rank_master: RankMaster = _rank_masters.get(_current_rank_id)
    if rank_master == null:
        _warn_missing_rank_master()
        return
    if rank_master.limit_turn <= 0:
        push_error("現在ランクのlimit_turnが不正なため試験を開始できません: %s" % _current_rank_id)
        return
    ...
```

しかし`_start_exam()`は`commit_rank_outcome()`の`outcome == RankOutcome.Value.PROMOTION_ELIGIBLE and not _in_exam`分岐からのみ呼ばれ、`outcome`は直前の`evaluate_rank_outcome()`で決定される。`evaluate_rank_outcome()`は以下の通り、`rank_master == null`の場合に**PROMOTION_ELIGIBLEへ到達する前に`CONTINUE`を返して打ち切る**。

```gdscript
func evaluate_rank_outcome() -> RankOutcome.Value:
    if not _rank_state_initialized:
        return RankOutcome.Value.CONTINUE
    var rank_master: RankMaster = _rank_masters.get(_current_rank_id)
    if rank_master == null:
        _warn_missing_rank_master()
        return RankOutcome.Value.CONTINUE
    ...
```

同一呼び出しフレーム内で`_rank_masters`が書き換わることはないため、`evaluate_rank_outcome()`が`rank_master == null`でCONTINUEを返した時点で`commit_rank_outcome()`が`PROMOTION_ELIGIBLE`分岐に入ることはなく、結果として`_start_exam()`内の`rank_master == null`分岐は**公開APIの呼び出し経路からは到達不能**（デッドコード）である。

一方、`rank_master.limit_turn <= 0`分岐は到達可能であることを確認した（`evaluate_rank_outcome()`は`limit_turn`の値自体を弾かないため、`limit_turn<=0`のRankMasterでも`quota_cleared`次第でPROMOTION_ELIGIBLEに到達しうる）。実際、`test_game_state_start_exam.gd`の異常系テスト（`test_RankMasterのlimit_turnが不正な場合は試験を開始せずin_examがfalseのまま`）は`limit_turn<=0`分岐のみを検証しており、`rank_master == null`分岐を公開API経由で検証するテストは存在しない（存在させることも原理的に不可能）。

**影響**: 実害はない（`evaluate_rank_outcome()`側の同種ガードが先に効くため、`RankMaster`未登録時に試験が誤って開始されることはない）。ただし`_start_exam()`のnullガードは事実上死んだコードであり、Test StrategyのInterfacesコメント（「rank_master==nullまたはlimit_turn<=0の場合はpush_error()」）は誤解を招く記述になっている。design phaseで「意図的な二重構造」とユーザー確認済みとされているが、null分岐については「二重」ではなく「片方が到達不能」という実体である点は設計文書側の記述更新を検討する価値がある。

**推奨対応**: Critical/Warningではない（Info相当）。次のいずれかを検討: (a) コメントを「limit_turn<=0のみが実質到達するガードであり、null分岐は`evaluate_rank_outcome()`の同種ガードとの防御的重複」と明記する、(b) 到達不能なnullガードをそのまま維持する（安全側の防御的コーディングとして許容）。いずれもブロッカーではないため、本plan内での対応は不要。

### Issue-2（🔴 要判断）: `_commit_exam_success()`の次ランクRankMaster未登録フォールバックはAI推論補完

**該当箇所**: `atelier/autoload/game_state.gd` L556-573（`_commit_exam_success()`）

task011のタスクファイルは「次ランクがあれば昇格・rank_state再初期化」とのみ記述しており、design phaseの擬似コードには「次ランクのRankMasterが`_rank_masters`に存在しない場合」の分岐が明記されていなかった。実装ではこの状況に対して以下のフォールバックを追加している。

```gdscript
func _commit_exam_success() -> void:
    var next_rank_id := RankProgression.get_next_rank_id(_current_rank_id)
    if next_rank_id == &"":
        _in_exam = false
        return

    var next_rank_master: RankMaster = _rank_masters.get(next_rank_id)
    if next_rank_master == null:
        push_error("次ランクのマスターデータが見つかりません: %s" % next_rank_id)
        return
    ...
```

実装コード自身のコメントで「🔴 NFR-101。次ランクのRankMasterが`_rank_masters`に未登録の場合は、`_start_exam()`のガードパターンに合わせ、確認が取れるまで一切の状態を変更せずpush_error()のみ行う」と明記されており、実装者自身がAI推論による補完であることを自己申告している。`_start_exam()`の`limit_turn<=0`ガードと同様のフェイルセーフパターンを踏襲した設計判断であり、既存のNFR-101（「試験開始不可」フォールバック）の思想と整合する。

このフォールバック分岐は`test_game_state_exam_outcome.gd`の`test_次ランクのマスターデータが未登録ならcurrent_rank_idとrank_stateが変更されない`でテストカバレッジ済み（`current_rank_id`・`rank_state.quota`が変更されないことを確認）。

**影響**: この分岐に入った場合、`in_exam`が`true`のまま・`_last_exam_outcome`が`SUCCESS`のまま残る（`_in_exam = false`の代入がreturnより前に実行されないため）。次回`commit_exam_outcome()`が呼ばれた際、`is_game_over()`がfalseなら再度`evaluate_exam_outcome()`が再評価され、同じ`exam_quota<=0`条件下では再度SUCCESS→同じフォールバックに入り続ける（無限に同じpush_error()を繰り返すのみで、状態破壊やクラッシュには至らない）。「詰み状態からの回復手段がない」という点は、実データ（`res://data/ranks/*.tres`）整備がplan外（CON-006/FR-405）である現段階では許容範囲内と考えられる。

**推奨対応**: Critical/Warningではない（Info相当、次plan以降でのランクマスター実データ整備時に自然に解消される想定）。design phase文書側にこのフォールバック仕様を正式に追記し、AI推論補完から確定仕様への格上げを検討することを推奨する。
