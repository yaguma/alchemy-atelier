## ペルソナ

### ペルソナ1: プレイヤー

- **役割**: 「Atelier」をプレイする個人開発ゲームのエンドユーザー
- **目的**: ギルドランクを昇格させながら、調合・納品のサイクルを繰り返して物語を進めたい
- **技術レベル**: ゲームプレイのみ（GDScript等の実装知識は不要）

### ペルソナ2: 開発者（実装者・保守担当）

- **役割**: 本plan（`rank-up`）を実装・レビュー・将来保守するGodot/GDScript開発者
- **目的**: `PromotionExamResolver`等のFunctional Coreを安全にテストし、`GameState`統合部分を壊さず将来のUI実装（別plan）に引き継ぎたい
- **技術レベル**: 上級（Godot 4.x + GDScript、Feature-Based Architecture、GdUnit4に習熟）

## エピック1: 昇格試験への突入

### US-001: ランクノルマを制限ターン内に達成し、昇格試験が自動的に始まる 🔵

**私は** プレイヤー **として**
**制限ターン到達時点でランクノルマを0にしていた場合、自動的に昇格試験へ突入したい**
**そうすることで** 通常プレイの延長として次ランクへの挑戦権を得られ、プレイの区切りを意識できる

- **関連要件**: FR-101, FR-007, FR-008, FR-009
- **優先度**: Must Have
- **受入基準**: AC-006

### US-002: 試験が二重に始まって進行中の状態が壊れない 🟡

**私は** 開発者 **として**
**`commit_rank_outcome()`が繰り返し呼ばれても`in_exam`中の試験状態が上書きされないようにしたい**
**そうすることで** 呼び出し順序に依存した不具合（試験ノルマの巻き戻り等）を未然に防げる

- **関連要件**: FR-201, FR-010
- **優先度**: Should Have
- **受入基準**: AC-017, AC-012, AC-013

### US-003: 試験の進行状況を将来のUI実装が参照できる 🔵

**私は** 開発者（将来のUI実装担当） **として**
**`GameState.get_state()`から試験の進行状況（`in_exam`/`exam_quota`/`exam_quota_max`/`exam_elapsed_turn`/`exam_turn_limit`）を取得したい**
**そうすることで** 別plan（UI実装）が本plan完了後にすぐ画面表示へ着手できる

- **関連要件**: FR-009
- **優先度**: Should Have
- **受入基準**: AC-018

## エピック2: 昇格試験中のプレイ

### US-101: 調合を実行して試験ターンを進める 🔵

**私は** プレイヤー **として**
**試験中に調合を実行すると、その調合実行自体が試験の1ターン消費としてカウントされてほしい**
**そうすることで** 通常プレイと同じ操作感で試験に挑める

- **関連要件**: FR-102, FR-003
- **優先度**: Must Have
- **受入基準**: AC-007

### US-102: 在庫が尽きても調合せずにターンだけ進めて詰みを回避する 🔵

**私は** プレイヤー **として**
**試験中に投入できる素材や解禁レシピが尽きた場合でも、調合を実行せずターンだけ進める操作をしたい**
**そうすることで** 詰み（デッドロック）状態のまま試験が進行不能になることを避けられる

- **関連要件**: FR-103, FR-104
- **優先度**: Must Have
- **受入基準**: AC-008

### US-103: 試験中に納品して試験ノルマを削る 🔵

**私は** プレイヤー **として**
**試験中の納品では、その日の指定調合物ボーナスに関わらず、報酬・貢献度が通常どおり計算されて試験ノルマに反映されてほしい**
**そうすることで** 通常プレイで培った在庫構成をそのまま試験に活かせる

- **関連要件**: FR-105, FR-106, FR-401
- **優先度**: Must Have
- **受入基準**: AC-009, AC-010

### US-104: 試験ロジックを副作用なく単体テストできる 🔵

**私は** 開発者 **として**
**`PromotionExamResolver`の各関数が乱数・`GameState`参照・in-place変更を一切持たない純粋関数であってほしい**
**そうすることで** GdUnit4でのユニットテストがモック不要かつ決定的に書け、将来の改修時のデグレを早期検知できる**

- **関連要件**: FR-001, FR-402, FR-403
- **優先度**: Must Have
- **受入基準**: AC-020

## エピック3: 昇格試験の結果確定

### US-201: 試験に成功して次ランクへ昇格する 🔵

**私は** プレイヤー **として**
**試験ノルマを試験制限ターン内に0にできたら、次ランクへ昇格し、降格回数カウンタもリセットされてほしい**
**そうすることで** 苦労して積み上げた成果が確実にランクへ反映される

- **関連要件**: FR-108, FR-004, FR-007, FR-010
- **優先度**: Must Have
- **受入基準**: AC-012

### US-202: 最高ランク（Sランク）で試験に成功し、ゲームクリアを迎える 🟡

**私は** プレイヤー **として**
**Sランクの試験に成功した場合、次ランクへの昇格ではなくゲームクリアとして扱われてほしい**
**そうすることで** ゲームの最終目標を達成した実感を得られる

- **関連要件**: FR-109, FR-404, FR-010
- **優先度**: Must Have
- **受入基準**: AC-013

### US-203: 試験に失敗して同ランクに再挑戦する 🔵

**私は** プレイヤー **として**
**試験制限ターン内にノルマを0にできなかった場合、同ランクの状態がリセットされて通常プレイに戻り、再挑戦できるようにしたい**
**そうすることで** 一度の失敗でゲームが即終了せず、立て直しの機会を得られる

- **関連要件**: FR-110, FR-004
- **優先度**: Must Have
- **受入基準**: AC-014

### US-204: 何度も試験に失敗し続けるとゲームオーバーになる 🔵

**私は** プレイヤー **として**
**同ランクでの再挑戦（試験失敗）が規定回数に達したら、ゲームオーバーとして明確に区切ってほしい**
**そうすることで** 「詰み」状態でだらだらプレイを続けさせられず、リザルトへ進める**

- **関連要件**: FR-111
- **優先度**: Must Have
- **受入基準**: AC-015

### US-205: 試験結果の確定処理が安全に何度呼ばれても壊れない 🟡

**私は** 開発者 **として**
**`commit_exam_outcome()`が`CONTINUE`中やゲームオーバー確定後に誤って複数回呼ばれても、状態が二重に変化しないようにしたい**
**そうすることで** UI実装（別plan）側の呼び出しタイミングのバグがゲーム状態を破壊するリスクを下げられる

- **関連要件**: FR-112, FR-113, FR-301
- **優先度**: Should Have
- **受入基準**: AC-016
