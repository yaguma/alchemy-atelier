## ペルソナ

### ペルソナ1: 錬金術師プレイヤー

- **役割**: ゲームのプレイヤー。ゴールドを稼ぎながらランクを昇格させ、恒久投資・消耗投資で自分の工房を強化していく
- **目的**: ランク間の工房強化画面で恒久投資（投入枠+1／庭拡張／レシピ解禁）に投資し、ターン中は消耗投資（触媒／種の指名買い）で戦術の幅を広げたい
- **技術レベル**: ゲームプレイヤー（実装詳細は意識しない。本plan自体はUIを持たないため、このペルソナの体験は`GameState.apply_upgrade()`が正しく振る舞うことで間接的に実現される）

### ペルソナ2: 後続UI実装者（Workshop Screen開発者）

- **役割**: 本plan（Domain層基盤＋GameState統合）の上に、別planで`WorkshopScreen`（UI層）を実装するエンジニア
- **目的**: `PurchaseValidator`と`GameState.apply_upgrade()`が設計文書通りの契約で動作することを信頼し、UI側は先出し判定のみを担い、最終防御は`GameState`側に任せたい
- **技術レベル**: 上級（プロジェクトのアーキテクチャルール・Functional Core/Imperative Shell原則を理解している）

## エピック1: 恒久投資の購入（ランク間限定）

### US-001: 投入枠を強化したい 🔵

**私は** 錬金術師プレイヤー **として**
**ランク昇格直後の工房強化画面で「投入枠+1」を購入したい**
**そうすることで** 次のランクから調合台によりたくさんの素材を同時投入し、品質と特性の取捨選択の幅を広げられる

- **関連要件**: FR-008, FR-101, FR-104, FR-105, FR-110, FR-114, FR-202
- **優先度**: Must Have
- **受入基準**: AC-001, AC-004, AC-007, AC-008

### US-002: 庭を拡張したい 🔵

**私は** 錬金術師プレイヤー **として**
**工房強化画面で「庭拡張」を購入したい**
**そうすることで** 同時に育てられる苗の数が増え、次ランクに向けた素材の仕込みを前倒しできる

- **関連要件**: FR-008, FR-101, FR-104, FR-106, FR-202
- **優先度**: Must Have
- **受入基準**: AC-004, AC-007, AC-009

### US-003: 新しいレシピを解禁したい 🔵

**私は** 錬金術師プレイヤー **として**
**工房強化画面で「レシピ解禁」を購入したい**
**そうすることで** 初期解禁レシピ以外の調合物を作れるようになり、狙える貢献度・報酬の幅が広がる

- **関連要件**: FR-007, FR-008, FR-101, FR-104, FR-107, FR-202
- **優先度**: Must Have
- **受入基準**: AC-004, AC-007, AC-010, AC-016

### US-004: 工房強化画面を離れたら恒久投資できないようにしたい 🔵

**私は** 錬金術師プレイヤー **として**
**（あるいは後続UI実装者として）工房強化画面を閉じた後は恒久投資を購入できないようにしてほしい**
**そうすることで** 通常ターン中に誤って恒久投資ボタンを押してしまうような不整合な購入経路を防げる

- **関連要件**: FR-002, FR-009, FR-015, FR-103, FR-110, FR-111, FR-201, FR-202
- **優先度**: Must Have
- **受入基準**: AC-004, AC-005

## エピック3: 購入の安全な検証

### US-201: UI判定が古くても不整合な購入を防いでほしい 🔵

**私は** 後続UI実装者 **として**
**UI側の先出し判定が古くても、`GameState.apply_upgrade()`が実行直前に必ず`PurchaseValidator.can_purchase`を再評価してくれることを期待する**
**そうすることで** ゴールドがマイナスになる、恒久投資が意図せず購入されてしまう等の不整合を防ぎ、安心してUIを実装できる

- **関連要件**: FR-001, FR-003, FR-101, FR-102, FR-401, FR-402, FR-403
- **優先度**: Must Have
- **受入基準**: AC-001, AC-002, AC-003, AC-014

### US-202: 購入回数の上限を超えて恒久投資できないようにしてほしい 🔵

**私は** 後続UI実装者 **として**
**「投入枠+1」のような`max_purchase_count = 1`の恒久投資が、購入済みなら2回目以降拒否されることを期待する**
**そうすることで** 投入枠+1の多重購入によるバランス崩壊（無制限に投入枠が増え続ける等）を防げる

- **関連要件**: FR-001, FR-010, FR-013, FR-102, FR-113
- **優先度**: Must Have
- **受入基準**: AC-001, AC-013

## エピック4: マスターデータ整備

### US-301: 5種類のUpgradeMasterが実データとして揃っていてほしい 🟡

**私は** 後続UI実装者（およびこのplanの実装者自身） **として**
**投入枠+1／庭拡張／レシピ解禁／触媒常備／種の指名買いの5種類の`UpgradeMaster` `.tres`が`res://data/upgrades/`に揃っていることを期待する**
**そうすることで** `PurchaseValidator`と`apply_upgrade()`の動作を実データを使った統合テストで検証でき、後続のUI実装時にも即座に一覧表示に使える

- **関連要件**: FR-004, FR-005, FR-006, FR-011, FR-115, FR-404
- **優先度**: Must Have
- **受入基準**: AC-015

### US-302: レシピ解禁購入の対象となる第2レシピが存在してほしい 🔵

**私は** このplanの実装者 **として**
**`recipe_healing_potion`以外の第2の`RecipeMaster` `.tres`が用意されていることを期待する**
**そうすることで** `recipe_unlock`効果の統合テスト（購入前は未解禁、購入後は`_unlocked_recipe_ids`に追加される）を実データで書ける

- **関連要件**: FR-007
- **優先度**: Must Have
- **受入基準**: AC-016

