## Coding Conventions

### Naming

| Target | Convention | Example |
|--------|-----------|---------|
| 変数・関数 | snake_case | `material_list`, `calculate_quality` |
| クラス（`class_name`） | PascalCase | `QualityCalculator`, `GameState` |
| シグナル | snake_case（過去形） | `phase_changed`, `gold_changed` |
| 定数 | UPPER_SNAKE_CASE | `CATALYST_TAG`, `GAME_BALANCE` |
| ファイル | snake_case | `quality_calculator.gd` |
| テストファイル | `test_{対象名}.gd` | `test_quality_calculator.gd` |
| テスト関数名 | 日本語の説明的な文（`test_`+説明+`() -> void:`） | `test_触媒タグ保有時に品質へボーナスが加算される()` |

### 型安全性（🔵 実コードで確認済み・厳格に遵守されている）

- 全引数・戻り値・signal引数に型注釈を付与（`Variant`の無条件使用は未検出）
- `logic/`層の関数はすべて`static func`（純粋関数、副作用なし）
- クラスレベル定数は`const`（例: `const CATALYST_TAG := &"catalyst"`）

### Error Handling

- 例外を投げず、専用の**Result型**（`shared/entities/result.gd`）でsuccess/failureを表現
- 内部エラーは`push_error()` / `push_warning()`で記録（`print()`は使用しない）
- `reset_for_test()`等のテスト専用APIは`assert(OS.is_debug_build(), ...)` + `if not OS.is_debug_build(): push_error(...)`の二重ガードで本番誤爆を防止

### 状態の防御的コピー

- `GameState.get_state() -> Dictionary`は内部状態を直接返さず、`Dictionary`/`Array`は`duplicate(true)`、`RefCounted`派生は`.clone()`で防御的にコピーしてから返す（呼び出し元からの直接改変を防ぐ）

### Import Style（GDScriptにimport文はない）

- `class_name`宣言済みクラスはグローバル解決で直接参照（推奨）
- `class_name`を持たない補助ファイル（テストフィクスチャ等）のみ`const X = preload("res://...")`

### コメント規約

- Public関数には`##`docコメント
- 重要な設計判断・注意点にはインラインで🔵🔴🟡マーカー付きコメント（ルールファイルの信号機システムと同一運用）
- 仕様書参照は`FR-###` / `AC-###`形式で対応付け

### テスト構造

- 実際のテストファイルは`extends GdUnitTestSuite`直下にフラットな`test_*()`関数を並べ、`# 正常系` / `# 異常系` / `# 境界値`のコメントで分類（ルール文書のネストクラス例`class TestNormalCases: extends GdUnitTestSuite`は実コードでは未使用、実質等価な運用）
- アサーションは`assert_int(...).is_equal(...)`スタイル（gdUnit4標準）
- 各テストはヘルパー関数（例: `_make_material()`）でその場でデータ構築、before_test/after_teardownへの依存を避ける

## Additional Notes

- **プロジェクト現況（2026-08-15時点）**: Phase 1基盤構築完了。`alchemy`（調合）・`garden`（庭）のDomain層（`logic/`）・State層（`state/`）・Resources層は実装済み、`guild`/`rank`/`workshop`は空スタブ。UI層（`ui/`）は全Featureで未着手（Phase 2のスコープ）。
- **アーキテクチャ原則**: Feature-Based Architecture（`features/{feature}/{logic,state,resources,ui}/`）+ Functional Core, Imperative Shell（`logic/`は`static func`・副作用なし、`autoload/`と`ui/`が副作用を担う）。他Featureから参照してよいのは`logic/*.gd`と`resources/*.gd`のみ（`state/`・`ui/`への直接参照禁止）。詳細: `.claude/rules/architecture.md`
- **コミット前必須チェック**: gdUnit4全テスト → gdlint → gdformat --check の3点、全てパスしてからコミット（`.claude/rules/implement-workflow.md`）
- **Git運用**: コミットメッセージは`<type>: <日本語subject>`（Conventional Commits準拠）。`git rebase`禁止、mainへの直接コミット禁止、PRは`--no-ff`相当のマージコミットで統合。詳細: `.claude/rules/git-workflow.md`
- **TDD原則**: `logic/`配下の純粋関数・`ui/`配下のUIはTDDモード（Red→Green→Refactor）、設定変更・ドキュメント更新等はDirectモード。詳細: `.claude/rules/tdd-implementation.md`
- **ドキュメントマップ**: ゲームコンセプト・要件定義・技術設計は`docs/concept/`・`docs/spec/`・`docs/design/atelier-alchemy-core/`配下に整備済み（詳細はリポジトリルート`CLAUDE.md`「ドキュメントマップ」参照）
- **既知の罠**（`.claude/rules/testing.md`参照）: `monitor_signals(obj)`の第2引数省略でAutoload（`GameState`）が誤って自動解放される既知の障害パターンあり。Autoloadを監視する場合は必ず`monitor_signals(obj, false)`を明示すること
